# OpenAI and Bedrock provider modules for SPARK-61672, second adversarial pass

Second review of `ai-openai` and `ai-bedrock` after the author addressed the 17 findings from the first pass. Each was re-verified against the current source. 14 are resolved, 2 are partial (half-open attribution, client leak), and 1 (Bedrock `attempts`) was left as is.

The fixes introduced their own defects. Sharing the pacer per endpoint with "strictest wins" and no release path turns a session-settable option into an irreversible, executor-wide throttle for every other user. Keying the client cache on per-call tuning (including a `Float` temperature on Bedrock) lets a session mint an unbounded number of `HttpClient`/Netty clients on each executor. The half-open breaker admits one probe but attributes every completion to the current state, so a late result from a call that started before the trip can close or re-trip it. And `requestTimeoutMs` only bounds time-to-headers, so a trickled body is unbounded.

**Watch for:** session-settable `ratePermitsPerSec` tightens the shared pacer for all catalogs on the executor, permanently (confirmed). Bedrock client cache keyed on `temperature` and `maxTokens`, OpenAI on `maxElapsedMs` etc., gives a session unbounded client/thread creation (confirmed). Stale completions mutate breaker state regardless of when the call was admitted (confirmed). `HttpRequest.timeout` does not cover body read, so a slow body holds the row open past every configured limit (confirmed). `CIRCUIT_OPEN` fatal in all three forms converts a 30 s provider blip into job failure on default `spark.task.maxFailures` (confirmed; trade-off stated below).

**Verdict**: NEEDS_CHANGES

## High-level view

Trust boundary. `credentialEnv` as a catalog option is rejected and the name comes only from `spark.ai.openai.credentialEnv`. Every numeric limit flows through `tighten`, which clamps to a cluster ceiling and uses the hard-coded default as the ceiling when the administrator sets none. That makes the defaults security ceilings, which is right, but it is undocumented and changes what "default" means for `maxElapsedMs` (60 s) and `requestTimeoutMs` (30 s). The rate ceiling cannot be disabled or raised when set; when unset, the session may set any rate including zero, as intended.

Shared endpoint state. Breaker and pacer are now looked up by `baseUrl|chatModel` and tightened monotonically. For the breaker this is safe because its policy is cluster-only. For the pacer it is not: the rate is session-settable, `Pacer.tightenTo` only ever lowers the interval, and nothing raises it again. One session sets `ratePermitsPerSec=1` on the approved endpoint and every query from every user on that executor is paced at 1/s until the executor dies.

Client cache. `forSettings` keys on a connection key that includes per-call fields. On OpenAI that is `maxAttempts|maxElapsedMs|requestTimeoutMs|maxResponseBytes|ratePermitsPerSec`; on Bedrock it is `maxTokens|temperature|apiCallTimeoutMs|apiCallAttemptTimeoutMs`. Each distinct value creates a new `HttpClient` (selector thread) or `BedrockRuntimeAsyncClient` (Netty event loop group), never closed. The first-pass finding said "bound the map or key by connection fields only"; the author did the latter but kept per-call fields in the key.

Breaker state machine. The CLOSED/OPEN/HALF_OPEN transitions and the CAS single-probe admission are correct for calls admitted under the current state. The defect is attribution: `recordSuccess` sets CLOSED unconditionally and `recordFailure`/`recordNeutral` act on whatever state they observe, with no notion of which generation admitted the call. With 16 calls in flight at trip time, their late outcomes close, re-trip, or re-probe the breaker during the window it is supposed to hold. `probeOut` is written and never read.

Time bounds. The size cap now streams and the Content-Length pre-check returns a sentinel. But `HttpRequest.timeout` fires only if response headers do not arrive in time; once headers are in, body delivery is unbounded, and `maxElapsedMs` is checked only between attempts. The `replacing` sentinel path also still reads and discards the whole oversized body over the wire; the comment "do not read the body at all" is wrong.

Fatal `CIRCUIT_OPEN`. The author made it fatal in all three forms to avoid hiding an outage as NULLs. On an executor where the breaker trips, every task that submits a row fails; Spark retries each task up to `spark.task.maxFailures` (4) and, without executor exclusion, lands on the same executor inside the 30 s window. The job fails. `generate_status` exists to report codes; returning an ERROR struct with `CIRCUIT_OPEN` there surfaces the outage without failing the job. `generate` should remain fatal. `try_generate` is the judgment call.

Harness. The two prior tautologies are now genuine tests. Breaker state is static and shared across tests, which silently degrades coverage: in the sanitization sweep, the third form for `m-slow` and `m-503-sanit` hits `CIRCUIT_OPEN` (threshold 3, two prior health failures on the same key), so `generate_status` sanitization of `TIMEOUT` and `SERVER_ERROR` is never exercised. The backoff-cancel test is probabilistic because full jitter allows a 0 ms backoff and attempts may be exhausted before the cancel.

## Status of the 17 first-pass findings

1. **Session-chosen `credentialEnv`**,  RESOLVED. `OpenAIFunctions.scala` `resolve`: `if (options.containsKey("credentialEnv")) throw ...`; value read from `conf("spark.ai.openai.credentialEnv")`. `CaseInsensitiveStringMap.containsKey` is case-insensitive. Harness case 1 covers it.
2. **Session-overridable limits**,  RESOLVED. `tighten(options, key, clusterLong(conf, key, DEFAULT))` for `maxInFlight`, `maxAttempts`, `maxElapsedMs`, `requestTimeoutMs`, `maxResponseBytes`; rate logic handles ceiling-unset, ceiling-set-with-zero-request, and ceiling-set-with-higher-request; breaker fields read from `clusterLong` only. Bedrock: `maxTokens`, `apiCallTimeoutMs`, `apiCallAttemptTimeoutMs` via `tighten`; `temperature` clamped to [0, 1]. Harness cases 2-4 cover it. New consequence in issue 1 below.
3. **Cancellation trips breaker**,  RESOLVED. `OpenAIClient.chatCompletion` `chain.whenComplete`: `if (isEndpointHealthFailure(failure.code)) recordFailure() else recordNeutral()`; `healthCodes = Set("TIMEOUT", "SERVER_ERROR", "RATE_LIMITED")`. Bedrock identical in `converse`. Harness "breaker ignores cancellation and client-side 400s" covers it.
4. **Size cap after buffering**,  RESOLVED. `boundedBodyHandler` returns `BodySubscribers.replacing(TOO_LARGE_SENTINEL)` on a declared length over cap, else `BoundedSubscriber`, which completes `done` with the sentinel and cancels the subscription once `total > maxBytes`. `classify` and `decode` test `eq TOO_LARGE_SENTINEL`. `BodySubscribers.replacing` and the JDK response wrapper return the same object reference, so `eq` holds (likely; confirmed by the chunked harness case passing). Two residuals in issues 4 and 11.
5. **Cancel during pacing or backoff**,  RESOLVED with a narrow residual. `Pacer.acquire(inFlight)` stores the wait future; backoff stores `wait` in `inFlight`; `sendWithRetry` checks `result.isCancelled` on entry and the pacer continuation checks it too. The race the author worried about (cancel between `httpFuture` completion and `inFlight.set(wait)`) is harmless because the entry check catches it. The residual is the mirror window: cancel between the entry check and `inFlight.set(httpFuture)` sends one request nobody cancels (issue 8).
6. **Bedrock `ValidationException` fatal**,  RESOLVED. `classify`: `"ValidationException" | "ModelErrorException" => "BAD_REQUEST"`, not in `fatalCodes`.
7. **Bedrock `SdkClientException` fatal**,  RESOLVED. `hasIoCause(root)` walks 16 levels of cause; IO -> `TIMEOUT`, else `CONFIG`. Note `ApiCallTimeoutException` subclasses `SdkClientException` but is matched first by simple name.
8. **No half-open state**,  PARTIAL. Real `CLOSED/OPEN/HALF_OPEN` with CAS admission exists and the harness proves one probe is admitted and its failure re-opens. Attribution of late outcomes is wrong (issue 3).
9. **Breaker/pacer bypass via second catalog**,  RESOLVED for bypass, and over-corrected: `endpointKey` sharing plus monotonic `tightenTo` means a session can now tighten for everyone (issue 1).
10. **Unbounded client leak**,  PARTIAL. The breaker and pacer are no longer part of the leak, but the client map is still unbounded and still keyed on session-controlled per-call fields, so it is still session-triggerable (issue 2).
11. **URLs in driver exceptions and `DESCRIBE`**,  RESOLVED. `description()` reports only `chatModel`; harness checks for `127.0.0.1` and `http`. The allowlist rejection message still echoes the rejected value. That is acceptable: the value is the caller's own catalog option, administrator-facing, and not a secret, and the harness depends on it. Claim (a) should say "prompt, token, provider body, and endpoint are never in a row-level error or plan", not "never in any exception". `canonicalName()` still embeds `baseUrl`; whether that string reaches `EXPLAIN` output depends on `ApplyAsyncFunctionExpression.toString`, not checked here (possible).
12. **Prefix-matched loopback**,  RESOLVED. `isLoopback` uses `URI.getHost` compared exactly against `127.0.0.1`, `localhost`, `[::1]`, `::1`; user info rejected. Harness covers the `127.0.0.1.attacker.example` case.
13. **Non-numeric Content-Length**,  RESOLVED. `firstValueAsLong` wrapped; `NumberFormatException` -> `OptionalLong.empty()`.
14. **Bedrock `attempts` hard-coded 1**,  NOT RESOLVED. `BedrockFunctions.success` and `failure` write `Integer.valueOf(1)` while the SDK's `standardRetryStrategy` retries up to 3 times. Severity LOW: a reported number that is known to be wrong is worse than NULL. Either write NULL for Bedrock, or attach a `MetricPublisher` and read `CoreMetric.RETRY_COUNT`.
15. **Cancellation test tautology**,  RESOLVED. The in-flight test asserts `slowWriteAborted == 1` (server's write failed because the client closed the socket) and the backoff test asserts no new server hit after cancel. Both are real on JDK 17+, where cancelling the `sendAsync` future aborts the exchange. Fragility in issue 10.
16. **NULL test could not detect a call**,  RESOLVED. `totalRequests` counts every request in the context handler; the test first proves the counter moves.
17. **Harness coverage**,  RESOLVED as scoped. Seven error models x three forms sweep, `generate_status` fatal, 32-caller concurrency, half-open probe, breaker isolation, shared-breaker-across-catalogs, chunked over-cap. Coverage silently lost to shared breaker state (issue 9).

<summary>Issues (12)</summary>

1. **Session-sticky executor-wide pacer** (HIGH, confirmed),  `OpenAIClient.pacerFor` shares one `Pacer` per `baseUrl|chatModel`; `Pacer.tightenTo` only lowers the interval and nothing ever raises it. `ratePermitsPerSec` is session-settable. Any user sets `ratePermitsPerSec=1` and every other catalog on that executor is paced at 1/s for the executor lifetime. Fix: the shared pacer must use only the cluster ceiling (`rateCeiling`); apply a session-requested lower rate in a per-client pacer layered on top, or track per-client rates and recompute the shared interval as the minimum of live registrations.
2. **Session-triggerable client/thread exhaustion** (HIGH, confirmed),  `BedrockClient.connectionKey` includes `maxTokens|temperature|apiCallTimeoutMs|apiCallAttemptTimeoutMs`; `OpenAIClient.connectionKey` includes `maxAttempts|maxElapsedMs|requestTimeoutMs|maxResponseBytes|ratePermitsPerSec`. All session-settable; `temperature` is a `Float`. Each distinct value creates a client with its own threads, never closed (`GenerateBound.close()` is a no-op, map never evicts). Fix: key clients on `region` (Bedrock) and `baseUrl|credentialEnv` (OpenAI) only; pass per-call tuning as arguments to `converse`/`chatCompletion` (Bedrock already builds `InferenceConfiguration` per request; timeouts can go on `request.overrideConfiguration`).
3. **Breaker mutated by stale completions** (MEDIUM, confirmed),  `CircuitBreaker.recordSuccess` sets `CLOSED` unconditionally; `recordFailure` and `recordNeutral` act on the observed state. A call admitted while CLOSED that completes after `trip()` closes the breaker (success), extends the OPEN window (health failure, `consecutiveFailures` restarts from 0 and re-trips), or flips HALF_OPEN back to OPEN-eligible while the real probe is still out (neutral), admitting a second probe. Both modules. Fix: stamp each admission with a generation counter incremented in `trip()` and ignore outcomes from earlier generations; in HALF_OPEN, only the probe's outcome may change state. Delete the unused `probeOut`.
4. **Body read not time-bounded** (MEDIUM, confirmed),  `HttpRequest.Builder.timeout` raises `HttpTimeoutException` only if response headers are not received in time. Once headers arrive, `BoundedSubscriber` reads until the server finishes; `maxElapsedMs` is checked only between attempts in `sendWithRetry`. A sick or hostile allowlisted endpoint that trickles the body holds the row and its in-flight slot indefinitely. Fix: race `httpFuture` against `delayed(remainingMs)` (or `orTimeout`), cancel the subscription on expiry, classify as `TIMEOUT`.
5. **Fatal `CIRCUIT_OPEN` in tolerant forms causes job failure** (MEDIUM, confirmed),  `fatalCodes` includes `CIRCUIT_OPEN` in both modules; `failure()` throws it for `Null` and `Status` modes. A tripped breaker fails every task on the executor; retries land on the same executor within `breakerResetMs` and exhaust `spark.task.maxFailures`. Trade-off: fatal guarantees an outage is never recorded as data, at the cost of converting a 30 s provider blip into job failure for users who chose the tolerant forms. Fix: `generate` stays fatal; `generate_status` returns the ERROR struct with `CIRCUIT_OPEN` (that is what the code column is for); `try_generate` returns NULL, or document loudly that the tolerant forms are not tolerant of breaker state. Alternatively make the breaker delay rather than reject while OPEN, bounded by `maxElapsedMs`.
6. **Pacer wait excluded from every deadline** (MEDIUM, confirmed),  `startNanos` is taken inside the `thenCompose` after `pacer.acquire`, and `acquire` reserves slots without bound. With many tasks on a paced endpoint a row can wait minutes before its first attempt, outside `maxElapsedMs` and `requestTimeoutMs`. Fix: take `startNanos` before `acquire` and fail fast with `RATE_LIMITED` if the computed wait alone exceeds `maxElapsedMs`.
7. **TLS failures retried and reported as `TIMEOUT`** (MEDIUM, confirmed),  `classify` maps any non-timeout, non-cancel throwable to `Retryable("TIMEOUT")`. An `SSLHandshakeException` (bad certificate, hostname mismatch) is retried `maxAttempts` times, counted as endpoint ill-health, and surfaced as "the request timed out". A certificate problem on an AI endpoint is a security signal and a configuration fault, not a transient. Fix: `case _: javax.net.ssl.SSLException => Terminal("CONFIG")` (fatal), with a sanitized message "TLS handshake failed".
8. **One uncancellable request in the pre-send window** (LOW, confirmed),  `sendWithRetry` checks `result.isCancelled`, then builds and sends; `inFlight.set(httpFuture)` happens after `sendAsync`. A cancel landing between the check and the set cancels the previous (completed) future and the new request runs to completion with prompt and token. Fix: after `inFlight.set(httpFuture)`, `if (result.isCancelled) httpFuture.cancel(true)`.
9. **Harness: shared breaker state silently removes coverage** (MEDIUM, confirmed),  `breakerFailureThreshold=3` cluster-wide; breakers are static per `base|model`. "request timeout surfaces TIMEOUT" records one health failure on `m-slow`; the sanitization sweep's `generate` and `try_generate` forms record two more and trip it, so the `generate_status` form receives `CIRCUIT_OPEN`, not `TIMEOUT`. Same for `m-503-sanit`. The sweep passes but never checks `TIMEOUT`/`SERVER_ERROR` sanitization in `generate_status`, and any new test that touches `m-503-always` once more will trip that key and cascade fatal `CIRCUIT_OPEN` into unrelated tests. Fix: expose `private[openai] def resetSharedStateForTests()` on `OpenAIClient` (clear `breakers`, `pacers`) and call it at the top of each `check`, or use a unique model name per test.
10. **Harness: backoff-cancel test is probabilistic** (LOW, confirmed),  `backoffMs(1, 0)` is `0..200 ms` full jitter, so by the 150 ms sleep anywhere from 1 to all 5 attempts may have completed; the test passes vacuously when attempts are exhausted before the cancel, and can fail spuriously if a request is on the wire when `sent` is read. Fix: add an `m-503-retry-after` model returning `Retry-After: 2`; cancel at 300 ms; assert exactly one hit.
11. **Over-cap `Content-Length` body is still fully read** (LOW, confirmed),  `BodySubscribers.replacing` is a discarding subscriber: it requests and drains the entire body so the connection can be reused. Memory is bounded; time and bandwidth are not, and the comment "Do not read the body at all" is false. Combined with issue 4 there is no bound on how long that drain takes. Fix: return a subscriber that cancels its subscription in `onSubscribe` and completes with the sentinel; accept that the connection is closed.
12. **Over-cap error bodies are terminal, not retried** (LOW, confirmed),  `classify` tests `eq TOO_LARGE_SENTINEL` before the status code, so a 503 or 429 whose body exceeds `maxResponseBytes` becomes terminal `RESPONSE_TOO_LARGE` and is not counted as endpoint ill-health. Fix: check status first; apply the sentinel check only on 2xx.

Also noted, not actionable as defects: defaults act as ceilings when the administrator sets none (`tighten` with `clusterLong(..., DEFAULT)`), which should be stated in the module doc and README; full jitter permits a 0 ms backoff and an immediate retry (consider equal jitter with a `base/2` floor); `rate.toInt` wraps for an absurd session value when no ceiling is set, harmlessly disabling pacing for that catalog only; an unknown `AwsServiceException` subclass with a 4xx status maps to `SERVER_ERROR` and counts toward the breaker.

### The pacer is now a shared, session-controlled, one-way throttle

```scala
private[openai] def pacerFor(s: OpenAISettings): Pacer = {
  val p = pacers.computeIfAbsent(endpointKey(s), _ => new Pacer())
  p.tightenTo(s.ratePermitsPerSec)
  p
}
...
def tightenTo(permitsPerSec: Int): Unit = {
  if (permitsPerSec > 0) {
    val wanted = 1000000000L / permitsPerSec
    intervalNanos.updateAndGet(cur => if (cur == 0L) wanted else math.max(cur, wanted))
  }
}
```

`ratePermitsPerSec` is exactly the limit the trust model says a session may lower, and lowering it now lowers it for everyone who shares the executor, with no path back. The doc comment calls this deliberate ("the pacer protects the endpoint, not a query"); the consequence it does not mention is that the lowest-privilege user on the cluster now controls the throughput of every other user's AI queries on that executor. Cluster ceiling in the shared pacer, session rate in a per-client pacer, and the trust model is intact.

### Client cache keyed on things a session chooses

```scala
// Bedrock
private def connectionKey(s: BedrockSettings): String =
  s"${s.region}|${s.modelId}|${s.apiCallTimeoutMs}|${s.apiCallAttemptTimeoutMs}|" +
    s"${s.maxTokens}|${s.temperature}"
```

Every field after `modelId` is session-settable and `temperature` is a `Float` in [0, 1]. Each distinct key builds a `BedrockRuntimeAsyncClient`, which allocates a Netty event loop group and connection pool, and the map never evicts. The OpenAI key has the same shape with `maxElapsedMs` (1..60000) and `requestTimeoutMs` (1..30000). The leak is real even for honest users, who will reasonably try a few tunings, and it is a one-line loop for a hostile one. `InferenceConfiguration` is already built per request in `converse`, so `maxTokens` and `temperature` do not need to be client state at all; the SDK accepts per-request timeouts via `AwsRequestOverrideConfiguration`. Same on the OpenAI side: `HttpClient` needs the base URL, the token, and a connect timeout (use the cluster ceiling); everything else belongs on the call.

### Breaker: right transitions, wrong attribution

```
t0  CLOSED, 16 calls admitted
t1  10 TIMEOUTs land -> trip() -> OPEN until t1+30s
t2  late call from t0 lands SUCCESS -> recordSuccess() -> CLOSED      (window cut short)
     or lands TIMEOUT  -> consecutiveFailures 1 of 10, or trip() again (window extended)
t3  OPEN expires, probe P admitted -> HALF_OPEN
t4  another late call from t0 lands BAD_REQUEST -> recordNeutral() sees HALF_OPEN
     -> state=OPEN, openUntil=now -> next tryAcquire admits probe Q while P is still out
```

The record methods are called from `chain.whenComplete` for every call that was ever admitted, and they only look at the current state. Nothing ties a completion to the state that admitted it. With `maxInFlight` 16 per task and several tasks per executor, dozens of calls are typically in flight when a trip occurs, and their outcomes land throughout the OPEN window. The practical effect is that the breaker's OPEN duration is random, and `HALF_OPEN` does not guarantee a single probe despite the comment and the harness case (which runs with no concurrent in-flight calls, so it cannot observe this). A generation counter bumped in `trip()` and captured at `tryAcquire` time fixes it; outcomes from an older generation are dropped. `probeOut` is set in three places and read in none.

### `CIRCUIT_OPEN` fatal: the trade-off

Making `CIRCUIT_OPEN` fatal is defensible for `generate`. For the tolerant forms the mechanics are: breaker trips on executor E; the next `produceResultAsync` on every task on E throws from inside `handle`; `AsyncEvalExec` sees a failed future and the task fails; the scheduler re-launches those tasks, by default on any executor including E; on E they fail again on their first row for as long as the breaker is OPEN or HALF_OPEN-with-probe-out (up to `breakerResetMs` + one probe's `maxElapsedMs`). Four quick failures and the job is gone. The author's concern that NULLs would hide an outage is valid for `try_generate`, which has no side channel. It is not valid for `generate_status`, whose `error_code` column is the side channel: an ERROR row with `CIRCUIT_OPEN` is precisely the observable the author wants, without the task-failure storm. The current code also means `generate_status` can never report `CIRCUIT_OPEN`, so the code exists in `sanitizedMessage` but can never appear in a row.

### Harness: state leaks between checks

Threshold 3, static `breakers`. Walk `base|m-slow`: "request timeout surfaces TIMEOUT" (1), sweep `generate` (2), sweep `try_generate` (3, trip). Sweep `generate_status` gets `CIRCUIT_OPEN`, fatal, thrown, message "AI_OPENAI_CIRCUIT_OPEN: the endpoint circuit is open", no secrets, PASS. The sweep asserts nothing about which code it got, so it cannot notice. `base|m-503-sanit` follows the same count. The sweep therefore proves sanitization of `TIMEOUT` and `SERVER_ERROR` in two of three forms, not three. Separately, `base|m-503-always` sits at two health failures after "retries stop at maxAttempts" and "absolute deadline"; one more test on that model trips it and every later use gets fatal `CIRCUIT_OPEN`. None of this is visible in a 58/58 PASS log.

The backoff-cancel check sleeps 150 ms and then reads the hit count. With full jitter the first backoff is uniform on [0, 200) ms and the second on [0, 400) ms, so by 150 ms the future may already have exhausted all five attempts (passes vacuously) or may have a request in flight that reaches the server after `sent` is read (fails spuriously). It passed this run.

### Remaining leak paths checked and not found

`num`, `required`, `optFloat`, and the `credentialEnv` rejection do not echo values. `OpenAIException` and `BedrockException` are built without a cause in every path; `asFailure` drops the original throwable. `HttpTimeoutException` and `HttpConnectTimeoutException` messages do not carry the URI, and are discarded anyway. Jackson parse failures are swallowed to `SCHEMA`. Bedrock classification is by class name; `AwsServiceException.getMessage` (which can echo prompt fragments on validation errors) is never read. `requestIdOf` bounds the untrusted header at 128 characters. The `CONFIG` message does not name the environment variable. `description()` no longer carries the URL. `canonicalName()` does; whether it reaches a plan string is unverified.
