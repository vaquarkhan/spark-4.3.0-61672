# OpenAI and Bedrock provider modules for SPARK-61672, third and final verification pass

All 12 round-2 findings were re-verified against the current source. 11 are resolved; one (R2#4, body time bound) is resolved for the row but not for the connection: the fix uses `orTimeout` on the `sendAsync` future and then calls `cancel` on that same, already-completed future, so a trickled body is cut off for the caller but the exchange keeps running in the background. The round-2 rewrite also introduced one new defect in the pacer: a caller rejected with `RATE_LIMITED` still consumes its slot, so a burst drifts `nextNanos` into the future and starves later callers, and that client-side rejection is counted as endpoint ill-health and can trip the breaker without a single request being sent.

**Watch for:** `orTimeout` returns `this`, so `httpFuture.cancel(true)` after a body-phase timeout is a no-op and the exchange, connection, and `BoundedSubscriber` buffer live on (confirmed). `Pacer.acquire` reserves a slot before deciding to reject (confirmed). Pacer `RATE_LIMITED` is in `healthCodes` (confirmed). The harness never exercises a trickled body, which is the exact path with the no-op cancel (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The trust boundary holds. `credentialEnv` is cluster-only and `CaseInsensitiveStringMap` lowercases keys, so `CREDENTIALENV` is caught. Client identity is `baseUrl|credentialEnv` (OpenAI) and `region` (Bedrock); both are allowlisted, so a session cannot mint clients. The 20-tuning harness case proves `clientCount` is flat. A missing credential throws `OpenAIException("CONFIG")` from inside `computeIfAbsent`; `ConcurrentHashMap` records no mapping on a throwing mapper, the message does not name the variable, and `AsyncEvalExec` catches a synchronous throw from `produceResultAsync` and restores the slot, so the map is not poisoned and the failure is fatal as intended.

The pacer split is correct in shape: the cluster pacer is built only from `clusterRatePermitsPerSec`, the session pacer only slows catalogs that asked for it, and the harness proves a 1/s session does not slow an unpaced catalog. The defect is inside `acquire`: `getAndUpdate` advances `nextNanos` before the `waitMs > maxWaitMs` check, so a rejected caller's slot is burned. After a burst, `nextNanos` sits far in the future and every later caller is rejected even though no requests are going out. That rejection is then recorded as a health failure against the shared breaker.

The breaker's generation stamping is correct for every ordering probed except one lock-free window: `tryAcquire` in CLOSED reads `state` and then `generation` non-atomically, so a caller that reads CLOSED a few nanoseconds before a trip picks up the post-trip generation and its later success closes the breaker during the window it should hold. Reversing the two reads (generation first) closes it. The stale third-call scenario (g0 call, g1 probe, g2 trip) is handled: g0 is ignored. The synchronized record methods and lock-free CAS do not lose updates; the state flips they race on are all re-checked under the lock.

Each attempt is now bounded for the caller. It is not bounded for the connection. `CompletableFuture.orTimeout` returns the receiver, so `timed eq httpFuture`; when the deadline fires, `httpFuture` is already completed with `TimeoutException` and `cancel(true)` returns false. The JDK aborts an exchange only when its returned future is cancelled, not when it completes exceptionally by other means, so the `BoundedSubscriber` keeps reading and the HTTP/1.1 connection stays occupied until the server finishes or the cap trips. The headers-phase path is unaffected because `HttpRequest.timeout` makes the JDK abort it itself, and that is the only path the harness tests.

Bedrock's single client per region is the right identity but now shares one Netty event loop and connection pool across every model and task on the executor. The default `maxConcurrency` is 50; `maxInFlight` 16 across 8 task slots is 128. Excess requests queue in Netty's pending-acquire queue and surface as `ApiCallAttemptTimeoutException` -> `TIMEOUT`, which counts toward the breaker. That is a capacity risk, not a defect, and it is fixable with one builder call.

<summary>Issues (6)</summary>

1. **Body-phase timeout does not abort the exchange** (MEDIUM, confirmed),  `orTimeout` returns `this`, so `timed eq httpFuture` and `httpFuture.cancel(true)` in `timed.whenComplete` is a no-op on an already-completed future; the JDK only aborts on cancellation, so the `BoundedSubscriber` keeps reading and the connection stays occupied until the server finishes or the cap trips. Each trickled attempt leaves a zombie exchange with up to `maxResponseBytes` buffered, unbounded in count. Fix: `val timer = scheduler.schedule(() => { timedOut.set(true); httpFuture.cancel(true) }, budget, MILLISECONDS)`; `httpFuture.whenComplete((_, _) => timer.cancel(false))`; in `classify`, map `CancellationException` to `Retryable("TIMEOUT")` when `timedOut` is set.
2. **Rejected pacer callers burn their slot** (MEDIUM, confirmed),  `Pacer.acquire` calls `nextNanos.getAndUpdate(...)` and only then compares `waitMs` to `maxWaitMs`; a rejected caller still advances `nextNanos` by one interval. A burst of N callers at rate R with budget T rejects everyone past T·R and leaves `nextNanos` N/R seconds ahead, so later callers are rejected while nothing is being sent. Fix: CAS loop,  compute the candidate slot from `prev`, return `RATE_LIMITED` without updating if the wait exceeds `maxWaitMs`, otherwise `compareAndSet`.
3. **Client-side pacer rejection counts as endpoint ill-health** (MEDIUM, confirmed),  `acquire` fails with `RATE_LIMITED`, which is in `healthCodes`, so `chain.whenComplete` calls `breaker.recordFailure`. A burst against a paced endpoint trips the shared breaker with zero requests sent, then every caller gets `CIRCUIT_OPEN` for `breakerResetMs`. Fix: fail the pacer with a distinct code (`PACED_OUT`, or `RATE_LIMITED` with a `local = true` flag) that is not a health code; same for the `remainingMs <= 0` `TIMEOUT` in `sendWithRetry` when `attempt == 1`.
4. **`tryAcquire` reads state before generation** (LOW, confirmed),  in the CLOSED arm, `state.get()` then `generation.get()` are two reads; a `trip()` between them hands the caller the post-trip generation, and that caller's success calls `recordSuccess` with a current gen and sets CLOSED inside the OPEN window. Fix: read `generation.get()` first, then `state.get()` (a stale gen is then always ignored), or make `tryAcquire` `synchronized`.
5. **Trickled body is untested** (LOW, confirmed),  "each attempt is bounded end to end" uses `m-slow`, which sleeps before sending headers, so it exercises `HttpRequest.timeout` only. Nothing in the harness sends headers promptly and trickles the body, which is the path with issue 1. Fix: add `m-trickle` (200 OK, chunked, 1 byte per 100 ms) with `requestTimeoutMs=500`, assert `TIMEOUT` and, via a server-side write-failure counter like `slowWriteAborted`, that the connection was closed.
6. **`sessionPacers` grows with distinct session rates** (LOW, confirmed),  keyed `endpoint|rate`, rate is any positive `Int` when no cluster ceiling is set, never evicted. Each entry is two atomics (no threads), so a hostile session can leak tens of MB per executor, not resources. Fix: bound the map (e.g. 1024 entries, fall back to the lowest registered rate) or round the rate to a small set of buckets.

Risks, not defects: (a) Bedrock one-client-per-region shares Netty's default `maxConcurrency` 50 across all tasks; `maxInFlight x task slots` commonly exceeds it, excess queues and surfaces as `ApiCallAttemptTimeoutException` -> `TIMEOUT` -> breaker (likely). Set `httpClientBuilder(NettyNioAsyncHttpClient.builder().maxConcurrency(ceiling x cores))`. (b) Two layers of pacing each receive `maxWaitMs = maxElapsedMs`, so total pacing wait can reach 2x before `sendWithRetry` returns `TIMEOUT`; pass the remaining budget to the second layer. (c) Session pacers are shared by every catalog that requests the same rate, so two catalogs at 4/s share 4/s; the scaladoc says "per-catalog". (d) `resetSharedStateForTests` is public on both production objects because the harness is in another package.

### `orTimeout` and the exchange that outlives its row

```scala
val httpFuture = http.sendAsync(request, OpenAIClient.boundedBodyHandler(s.maxResponseBytes))
val timed = httpFuture.orTimeout(attemptBudgetMs, TimeUnit.MILLISECONDS)   // returns httpFuture
timed.whenComplete { (_, e) => if (e != null) httpFuture.cancel(true) }     // already done: false
```

The Javadoc for `CompletableFuture.orTimeout` is explicit that it returns `this`. When the timer fires, `httpFuture` completes exceptionally with `TimeoutException`; `cancel(true)` on a completed future returns `false` and triggers nothing. The JDK's `sendAsync` contract aborts the exchange when the returned future is cancelled, which the harness proves works (`slowWriteAborted == 1` on explicit cancel), but an exceptional completion from outside is not a cancellation. The `BoundedSubscriber` continues to receive `onNext`, buffering toward `maxResponseBytes`, and the HTTP/1.1 connection is held until the server completes or the cap cancels the subscription. Each retried attempt against a trickling endpoint leaves another one. Memory per zombie is bounded by the cap; the count is not. The `HttpRequest.timeout` path is immune because the JDK fires that timer internally and aborts the exchange itself, which is why `m-slow` passes.

### The pacer gives back nothing

```scala
val slot = nextNanos.getAndUpdate(prev => math.max(now, prev) + intervalNanos)
val waitMs = math.max(0L, (slot - now) / 1000000L)
if (waitMs == 0L) ...
else if (waitMs > maxWaitMs) failedFuture[Void](new OpenAIException("RATE_LIMITED"))
```

At 4/s with `maxElapsedMs` 60 s, 1000 rows arriving together admit 240 and reject 760, but `nextNanos` ends 250 s ahead. For the next 190 s every new caller computes a wait above 60 s and is rejected, with the endpoint idle after the first 60 s. Every one of those rejections goes through `chain.whenComplete` -> `asFailure` -> `RATE_LIMITED` -> `isEndpointHealthFailure` -> `recordFailure`. Ten of them trip the shared breaker at default policy, so the burst converts into `CIRCUIT_OPEN` for every catalog on the endpoint, having sent nothing. The 32-caller harness case does not see this because 32 slots at 40/s is 0.8 s, far under the budget.

### Breaker read ordering

```scala
def tryAcquire(): Long = state.get() match {
  case CLOSED => generation.get()
  ...
```

Thread A reads `CLOSED`. Thread B completes `recordFailure` -> `trip()`, which bumps `generation` to g+1 and sets `OPEN`. Thread A reads `generation` = g+1 and is admitted into the OPEN generation. Its success calls `recordSuccess(g+1)`, `current` is true, state becomes CLOSED. One racing call reopens the endpoint to everyone during the hold window. Reading `generation` first removes the window: if the trip lands after both reads, A holds g and is stale; if between, A sees OPEN and takes the probe path; for A to see CLOSED again with a different gen a probe must have succeeded, bumping past g. The interleaving the author asked about (g0 call in flight, g1 probe fails, trip to g2, g0 lands) is correctly ignored.
