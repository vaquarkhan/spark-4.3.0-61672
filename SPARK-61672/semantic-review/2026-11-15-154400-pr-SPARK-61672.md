# OpenAI and Bedrock provider modules for the SPARK-61672 async function SPI

Two provider modules (`ai-openai`, `ai-bedrock`) implement `AsyncScalarFunction` behind a `FunctionCatalog`, resolve settings on the driver from `spark.sql.catalog.<name>.*` options clamped by `spark.ai.<provider>.*` cluster allowlists, ship a `Serializable` bound function to executors, and build one shared client per distinct settings tuple on the executor. The OpenAI module hand-rolls retry, Retry-After, a size cap, a pacer, and a circuit breaker over `java.net.http`; the Bedrock module delegates retry to the AWS SDK and adds the same breaker. A 42-case loopback harness is offered as proof of eight security and resilience claims.

Reviewed as a hostile reader of those eight claims. Three are false as stated, two more hold only because of mechanisms that break the tolerant forms, and two harness cases pass with the feature removed.

**Watch for:** `credentialEnv` and every limit other than `maxInFlight` are session-controlled, so a Connect user can send any executor environment variable as a Bearer token and disable the rate limiter and size cap (confirmed). Cancellation counts as a breaker failure, so one killed task with 16 in-flight calls opens the executor-wide breaker for 30 s (confirmed). The size cap is checked after the whole body is in memory (confirmed). A cancel during backoff or pacing still fires one more full HTTP request with the prompt and token (confirmed). Two harness checks are tautologies: the cancellation test asserts `f.isCancelled` after `f.cancel()`, and the NULL-input test counts hits that `m-ok` never increments (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The allowlist story covers `baseUrl`, `chatModel`, `region`, `modelId`, and `maxInFlight` and nothing else. Nine of the eleven OpenAI settings and seven of the nine Bedrock settings come straight from session-settable catalog options with only a `max(1, x)` floor. The one that matters most is `credentialEnv`: it names which executor environment variable becomes the `Authorization: Bearer` header, and nothing restricts it. The README's "Optional tuning (clamped to the ceiling)" sentence is false for every option it lists except `maxInFlight`.

The circuit breaker is shared per settings tuple across all tasks on an executor and increments on every failure, including `CANCELLED`, `BAD_REQUEST`, `SCHEMA`, and `RESPONSE_TOO_LARGE`. The engine's `cleanup()` cancels all outstanding source futures when a task ends, so a task killed with more than `breakerFailureThreshold` calls in flight opens the breaker for every other task on that executor. The documented half-open "one trial call" does not exist in the code.

The response size cap rejects oversized bodies but does not bound memory: `BodyHandlers.ofByteArray()` buffers the entire response before `decode` looks at its length. Only the gzip path checks incrementally, and even it reads from a fully buffered compressed array. A chunked response with no `Content-Length` is bounded only by executor heap.

Cancellation propagates correctly to an HTTP exchange that is in flight, but not to one that is about to start. During the pacer wait or a retry backoff, `inFlight` holds `null` or a completed future, and the continuation after `delayed()` sends a fresh request with the prompt and token after the engine has already given up on the row.

Bedrock's `ValidationException -> BAD_MODEL -> fatal` mapping makes per-row conditions (prompt exceeds the model context window, which Bedrock reports as `ValidationException`) kill the whole task in `try_generate` and `generate_status`. `SdkClientException -> CONFIG -> fatal` does the same for transient connection resets. Claim (e) holds, but by classifying row-level errors as fatal.

The harness proves the allowlist rejections, the clamp, gzip decoding, Retry-After arithmetic, and the retry/deadline counts. It does not prove cancellation, NULL short-circuit, breaker isolation, concurrency safety, or sanitization on any path other than a 400 in `generate`. Its own first test case produces an exception whose message contains the rejected URL, which contradicts claim (a) for driver-side errors, and nothing asserts on it.

1. **Session-chosen `credentialEnv` exfiltrates executor secrets** (HIGH, confirmed),  `OpenAIFunctions.scala` ~L137: `credentialEnv` is read from catalog options with no allowlist, so any session can set `spark.sql.catalog.x.credentialEnv = SENSITIVE_EXECUTOR_ENV` and the client sends that value as a Bearer token to an allowlisted endpoint. Fix: read `credentialEnv` from `conf("spark.ai.openai.credentialEnv")` only, or allowlist it like `baseUrl`.
2. **Rate limit, size cap, retry budget, and breaker threshold are session-overridable** (HIGH, confirmed),  `OpenAIFunctions.scala` ~L155-170 and `BedrockFunctions.scala` ~L145-160: `clusterRate` is only a default (`optInt(options, "ratePermitsPerSec", clusterRate)`), and `maxResponseBytes`, `maxAttempts`, `maxElapsedMs`, `requestTimeoutMs`, `breakerFailureThreshold`, `maxTokens` have no ceiling. A session can set `ratePermitsPerSec=0`, `maxResponseBytes=9e18`, `maxAttempts=1000000`. Fix: for each limit, `math.min(requested, conf("spark.ai.<p>.<limit>Ceiling"))`, and treat the cluster rate as a floor on the interval, not a default. Correct the README sentence.
3. **Cancellation trips the executor-wide circuit breaker** (HIGH, confirmed),  `OpenAIClient.scala` ~L81 and `BedrockClient.scala` ~L87: `recordFailure()` runs for every exceptional completion, including `CANCELLED`. `AsyncEvalExec.cleanup()` cancels all outstanding futures at task end, so a killed or early-terminated task with `maxInFlight >= breakerFailureThreshold` (defaults 16 >= 10) opens the breaker for 30 s for every task on that executor. Fix: `recordFailure()` only for `TIMEOUT`, `SERVER_ERROR`, `RATE_LIMITED`; never for `CANCELLED`, `BAD_REQUEST`, `SCHEMA`, `RESPONSE_TOO_LARGE`, `EMPTY`.
4. **Size cap is enforced after full buffering** (HIGH, confirmed),  `OpenAIClient.scala` ~L111 and ~L276: `BodyHandlers.ofByteArray()` reads the entire body into heap, then `decode` compares `raw.length > maxBytes`. The `Content-Length` pre-check is skipped by any chunked response. Fix: use a custom `BodySubscriber` (or `ofInputStream` plus a counting stream) that cancels the subscription once `maxBytes` is exceeded.
5. **Cancel during pacing or backoff still sends a request** (MEDIUM, confirmed),  `OpenAIClient.scala` ~L71-74 and ~L134-136: while waiting in `rateLimiter.acquire()` `inFlight` is `null`; while waiting in `delayed(delay)` it holds the previous completed future. `result.cancel()` cancels nothing, and the `thenCompose` continuation issues a fresh POST with prompt and token. Fix: pass `result` into `sendWithRetry` and return early if `result.isCancelled` before each `sendAsync`; store the `delayed` future in `inFlight` as well.
6. **Bedrock classifies row-level `ValidationException` as fatal** (MEDIUM, confirmed),  `BedrockClient.scala` ~L177: Bedrock returns `ValidationException` for "Input is too long for requested model" and similar per-prompt failures, which `fatalCodes` turns into a task failure even in `try_generate`. Fix: map `ValidationException` to non-fatal `BAD_REQUEST`; detect bad model id once at catalog init (or on first call) rather than per row.
7. **Bedrock classifies transient `SdkClientException` as fatal `CONFIG`** (MEDIUM, confirmed),  `BedrockClient.scala` ~L176: connection resets and DNS blips surface as `SdkClientException: Unable to execute HTTP request`, which becomes fatal `CONFIG`. Fix: inspect the cause chain for `IOException` and classify those as retryable `TIMEOUT`/`SERVER_ERROR`; reserve `CONFIG` for credential-chain and region failures.
8. **Breaker has no half-open state** (MEDIUM, confirmed),  `OpenAIClient.scala` ~L176-178 documents "one trial call is allowed after the reset window"; `check()` lets every caller through once `openUntilNanos` passes, and a success from a request started before the breaker opened closes it immediately. Fix: add a `halfOpen` CAS guard that admits one probe and re-opens on its failure; ignore results from calls started before `openUntilNanos` was set, or fix the doc comment.
9. **Breaker and pacer are trivially bypassed by a second catalog** (MEDIUM, confirmed),  `OpenAIClient.scala` ~L215-217: clients are keyed by `settings.toString`, so a catalog with `maxAttempts=5` instead of 4 gets a fresh breaker, fresh pacer, and fresh `HttpClient`. Fix: key the breaker and pacer by `(baseUrl, chatModel)` only; key the `HttpClient` by connection-relevant fields.
10. **Unbounded `HttpClient` / `BedrockRuntimeAsyncClient` leak per settings tuple** (MEDIUM, confirmed),  same lines plus `GenerateBound.close()` no-op: every distinct settings tuple creates a client with its own selector or Netty event-loop threads for the executor lifetime and nothing evicts it. Fix: bound the map (LRU with `close()` on eviction) or key clients by connection fields only.
11. **URLs and model ids appear in driver exceptions and in `DESCRIBE FUNCTION`** (MEDIUM, confirmed),  `OpenAIFunctions.scala` ~L115 and ~L217, `BedrockFunctions.scala` ~L109 and ~L196: `requireAllowed` echoes the rejected value; `description()` embeds `baseUrl`. Claim (a) says URLs never appear in any exception or plan. Fix: either drop the value from the message and the URL from `description()`, or narrow the claim to executor-side and row-level errors.
12. **Loopback exemption is prefix-matched** (LOW, confirmed),  `OpenAIFunctions.scala` ~L139-141: `http://127.0.0.1.attacker.example/v1` and `http://localhost.attacker.example/v1` pass the scheme check. Mitigated by the exact-match allowlist. Fix: parse with `URI` and compare `getHost` to `127.0.0.1`/`localhost`/`::1`.
13. **Non-numeric `Content-Length` escapes classification** (LOW, confirmed),  `OpenAIClient.scala` ~L297: `firstValueAsLong` throws `NumberFormatException` inside `handle`, which bypasses retry classification and lands as `SERVER_ERROR` (sanitized by `asFailure`, but not retried and counted by the breaker). Fix: wrap in `Try` and treat unparseable as absent.
14. **Bedrock `attempts` is hard-coded 1** (LOW, confirmed),  `BedrockFunctions.scala` ~L283 and ~L300: the SDK retries up to 3 times internally; the status struct always reports 1. Fix: read `response.sdkHttpResponse()` metrics or document the field as "client attempts" for Bedrock.
15. **Harness: cancellation test is a tautology** (HIGH, confirmed),  `ProviderConformanceHarness.scala` ~L376-378: `f.cancel(true); assertTrue(f.isCancelled)` passes for any `CompletableFuture`. Fix: have the `m-slow` handler record whether its write failed or the exchange was aborted, and assert that, or assert that no `hit` arrives for a second request after cancelling during backoff (which would currently fail, see issue 5).
16. **Harness: NULL-input test cannot detect a call** (HIGH, confirmed),  ~L243-247: `m-ok` never calls `hit()`, so `hits.values.sum` is unchanged whether or not a request is sent. Fix: add `hit("ok")` to the `m-ok` branch, or count requests in the context handler globally.
17. **Harness: sanitization is checked on one path; concurrency, half-open, status-fatal, and chunked-body paths are untested** (MEDIUM, confirmed),  ~L331-338 checks only `m-400` in `generate`. No test for `generate_status` on a fatal code, `CONFIG` (unset env var), TIMEOUT/SCHEMA message content, Bedrock sanitization through the catalog path, breaker reset, concurrent breaker/pacer behavior, or a chunked response over the cap. Fix: parameterize the leak check over all `m-*` models and all three forms; add the missing cases.

### Trust boundary: what the session controls

`OpenAIConf.resolve` enforces the allowlist on `baseUrl` and `chatModel` and clamps `maxInFlight`. Everything else is read from `options` with a floor only:

```scala
val credentialEnv = Option(options.get("credentialEnv")).map(_.trim)
  .filter(_.nonEmpty).getOrElse("AI_PROVIDER_TOKEN")
...
ratePermitsPerSec = math.max(0, optInt(options, "ratePermitsPerSec", clusterRate)),
maxResponseBytes  = math.max(1L, optLong(options, "maxResponseBytes", DEFAULT_MAX_RESPONSE_BYTES)),
maxAttempts       = math.max(1, optInt(options, "maxAttempts", DEFAULT_MAX_ATTEMPTS)),
```

Catalog options are `SQLConf` entries, which a Spark Connect client sets freely. The `credentialEnv` case is the serious one: `OpenAIClient` does `sys.env.getOrElse(settings.credentialEnv, ...)` and puts the value verbatim in `Authorization: Bearer`. A session that registers a second catalog pointing at an allowlisted endpoint with `credentialEnv = SENSITIVE_EXECUTOR_ENV` (or `SPARK_AUTH_SECRET`, or whatever the executor image carries) ships that secret to the endpoint operator on every row. Claim (b) is literally true (endpoint, model, concurrency cannot be widened) and the security story it supports is false: the session chooses which secret the allowlisted endpoint receives.

`spark.ai.openai.ratePermitsPerSec` is described as a cluster ceiling but is passed as the *default* for the catalog option, so `ratePermitsPerSec = 0` from a session disables pacing entirely. `maxResponseBytes` has no ceiling, so the size cap is a suggestion. Bedrock has the same shape for `maxTokens`, `apiCallTimeoutMs`, and the breaker settings; `maxTokens` unbounded is a direct cost control gap.

### Breaker shared across tasks, polluted by cancellation

```
task A (killed, 16 in flight)          OpenAIClient (shared per settings)
  AsyncEvalExec.cleanup()  ───────►  result.cancel(true)  x16
                                        └► httpFuture.cancel ─► handle: CANCELLED
                                             └► failedFuture ─► whenComplete(err != null)
                                                  └► breaker.recordFailure()  x16  (threshold 10)
task B (healthy, same executor)  ───►  breaker.check() == CIRCUIT_OPEN for 30 s
```

`OpenAIClient.chatCompletion`'s `whenComplete` and `BedrockClient.converse`'s `whenComplete` both call `recordFailure()` on any `err != null`. Nothing filters by code. `AsyncEvalExec.cleanup()` runs `requestCancel()` on task completion and interrupt, which cancels every outstanding source future. With defaults (`maxInFlight` 16, `breakerFailureThreshold` 10), a single `LIMIT` query that stops a task early, or a speculative duplicate killed by the scheduler, opens the breaker for all other tasks on the executor. In `try_generate` that silently turns 30 s of rows into NULLs; in `generate` it fails other tasks with `CIRCUIT_OPEN`.

The same lack of filtering means ten rows with prompts that the endpoint rejects with 400 open the breaker, so client-side input problems are treated as endpoint outages.

The doc comment on `CircuitBreaker` promises "One trial call is allowed after the reset window." `check()` returns `None` for every caller once `System.nanoTime() >= until`; there is no half-open latch. Under load, every in-flight slot fires a probe simultaneously. `recordSuccess()` also sets `openUntilNanos = 0` unconditionally, so a slow success from before the trip closes the breaker the moment it lands.

### Size cap after the fact

```scala
val httpFuture = http.sendAsync(request, HttpResponse.BodyHandlers.ofByteArray())
...
val raw = resp.body()
...
if (raw.length > maxBytes) throw new OpenAIException("RESPONSE_TOO_LARGE")
```

The body is fully materialized before the comparison. The `Content-Length` pre-check in `classify` catches honest servers; a chunked response (no `Content-Length`) or a lying one is buffered to completion. The gzip loop does check `total > maxBytes` before `out.write`, which is the right order, but it inflates from a compressed array that was itself fully buffered. Claim (c) is true about rejection and false about protection: the cap protects downstream parsing, not executor heap. Mitigation is that the endpoint is admin-allowlisted, so the attacker must own or compromise an approved endpoint.

### Cancellation gaps between attempts

`chatCompletion` cancels `inFlight.get()` when `result` is cancelled. `inFlight` is set only inside `sendWithRetry` after `sendAsync`. Two windows exist where cancelling does nothing useful:

During `rateLimiter.acquire()`: `inFlight` is `null`. The `thenCompose` continuation runs when the delay elapses and sends the request.

During `delayed(delay)` between attempts: `inFlight` holds the previous attempt's completed future; `cancel(true)` on it is a no-op. The continuation then calls `sendWithRetry(attempt + 1)` and sends the request.

In both cases the engine has already discarded the row, the request still carries the prompt and the token, and the result feeds `breaker.recordFailure()` or `recordSuccess()` on a future nobody observes. Claim (f) holds only for the window where an exchange is already on the wire. The harness cannot detect this because its cancellation check is `assertTrue(f.isCancelled)` immediately after `f.cancel(true)`, which `CompletableFuture` guarantees regardless of what the callback did.

Bedrock's `sdkFuture.cancel(true)` on an in-flight SDK future is the right call and the SDK does propagate it (likely; not traced through the SDK version in the pom).

### Bedrock fatal classification is too wide

```scala
case "SdkClientException" => "CONFIG"      // no credentials, bad region, no network
case "ValidationException" | "ResourceNotFoundException" => "BAD_MODEL"
```

Both codes are in `fatalCodes`. Bedrock's Converse API returns `ValidationException` for per-request problems that depend on the prompt: input exceeds the model's context length, unsupported content, some guardrail outcomes. One oversized row in a partition therefore fails the whole task in `try_generate` and `generate_status`, which exist precisely to survive that. `SdkClientException` is the SDK's wrapper for any transport failure ("Unable to execute HTTP request: Connection reset"), so a transient network blip is also fatal. The comment on the line acknowledges "no network" as a `CONFIG` case.

`getSimpleName` matching survives shading (relocation changes packages, not simple names). The problem is the mapping, not the mechanism.

### Sanitization: executor path is clean, driver path and plan are not

Executor-side, `OpenAIException` and `BedrockException` are constructed without a cause and `asFailure` drops the original throwable, so no exception chain reaches the engine with provider text in it; `followRedirects(NEVER)` keeps the Bearer token from being replayed to a redirect target.

Claim (a) still overreaches. `requireAllowed` throws `IllegalArgumentException(s"$kind '$value' is not on the cluster allowlist ...")` with the rejected URL or model id in the message; the harness's first test depends on that message and passes. `GenerateUnbound.description()` returns `... via ${settings.baseUrl}`, which `DESCRIBE FUNCTION` and catalog listings expose. Neither is a secret, but the claim says "never" and "any plan". Separately, `-Djdk.httpclient.HttpClient.log=headers` on an executor logs the `Authorization` header, and the AWS SDK's `software.amazon.awssdk.request` logger at DEBUG logs request bodies; the modules cannot prevent either, so "never in a log" needs a caveat.

A server-controlled `x-request-id` header is copied verbatim into the `request_id` column. Not a leak, but it is untrusted content in query output and has no length bound beyond the HTTP client's header limit.

### Client lifecycle and the settings-keyed map

`forSettings` keys on `settings.toString`, so any difference in any field produces a new `OpenAIClient` with its own `HttpClient`, `TokenBucket`, and `CircuitBreaker`. Since nine of those fields are session-controlled, a user who hits `CIRCUIT_OPEN` or is being paced can register a catalog with `maxAttempts = 5` and get fresh state. Each such client is also a permanent leak: `HttpClient` is never closed, the `ConcurrentHashMap` never evicts, and `GenerateBound.close()` is a no-op. Bedrock has the same structure with a Netty event loop per `BedrockRuntimeAsyncClient`.

The token is read once in the `OpenAIClient` constructor and cached for the executor lifetime, so rotating the environment variable has no effect until the executor restarts. Worth documenting.

### Attack vectors that did not land

Checked and not reproducible: allowlist bypass via trailing slash, case, `..` traversal, or userinfo (exact string match after a single `stripSuffix("/")` rejects all of them); serialization of anything non-transient with `GenerateBound`; `Integer` boxing for `IntegerType` in `GenericInternalRow`; Jackson echoing prompt text in a parse error (swallowed to `SCHEMA`); `Retry-After` overflow (`Long.MAX * 1000` wraps negative and clamps to 0); `whenComplete` not firing on `cancel()` (it does, cancellation is an exceptional completion); gzip loop ordering (the `total > maxBytes` check precedes `out.write`). Two small inaccuracies remain in this area: `TokenBucket` is a fixed-interval pacer with no burst capacity and an unbounded queue of delayed futures, not a token bucket; and the deadline check runs before the sleep, so a run can overshoot `maxElapsedMs` by up to one `requestTimeoutMs`.

### What the harness does not prove

The harness does establish allowlist rejection, the `maxInFlight` clamp, Jackson escaping, gzip decode and decoded-size cap, Retry-After arithmetic and timing, `maxAttempts` and deadline counts, 4xx classification, the `try_generate` NULL/fatal split, status struct population, breaker opening, and the Bedrock exception map. The live Bedrock cases ran (PASS, not "skipped"). It does not establish:

- Cancellation (issue 15): the assertion is a tautology.
- NULL short-circuit (issue 16): `m-ok` never increments a counter, so the before/after comparison is always equal.
- Plain-body size cap post-buffer path: `m-big` sends `Content-Length`, so the pre-check fires and `raw.length > maxBytes` is never reached. No chunked case.
- Sanitization on any path other than `m-400` via `generate`: no `AUTH`, `TIMEOUT`, `SCHEMA`, `CONFIG` (unset env var), `generate_status` error struct against the token/URL, or any Bedrock error through the catalog path.
- `generate_status` on a fatal code (should throw, not return a struct).
- Breaker reset, half-open, isolation across tasks, or that row-level 400s do not trip it (they do).
- Any concurrent execution of the breaker or pacer; the "safe under concurrency" part of claim (g) has zero coverage. The pacer test issues five calls sequentially from one thread with a 100 ms slack on a 1000 ms expectation.
- That two catalogs with different tuning share or do not share client state.
- Resource cleanup of any kind.
